title: Cards API
description: Endpoints para gestionar el inventario operativo local de tarjetas y sus asignaciones a vehiculos.

## Base

Base path: `/api/cards`

Todos los endpoints requieren autenticacion. La mayoria usa permisos `cards.*`; las acciones que ubican stock Cardcloud usan permisos `cardcloud-stock.*`. El borrado desactiva el registro cambiando `status` a `inactive`.

Este modulo representa tarjetas locales de operacion. No es el stock externo del proveedor; el stock sincronizado se administra desde `cardcloud-stock`.

## Alcance por compania

Requiere header `X-Company-Id: <companyId>`. Todas las operaciones quedan limitadas a esa compania. Si el acceso del usuario tiene `scopeKey: "subCompanyId"`, `subCompanyId`, `vehicleId` y la tarjeta consultada tambien deben pertenecer a una de esas subcompanias.

## Listado

`GET /api/cards`

Query params: `page`, `limit`, `search`, `all`, `status`, `subCompanyId`, `vehicleId`, `designFuelId`, `assignmentMode`.

`search` busca por `externalId`, `stock.externalId`, `stock.maskedPan`, `stock.clientId`, `stock.providerStatus`, `subCompany.key`, `subCompany.name`, `vehicle.plates`, `vehicle.economicNumber`, `designFuel.code` y `designFuel.name`.

Para columnas visibles, usa `stock.maskedPan`, `stock.clientId`, `stock.balance`, `stock.providerStatus`, `vehicle.plates`, `vehicle.economicNumber`, `designFuel.name` y `subCompany.name`.

Response `200`: resultado paginado de `Card`.

## Exportar tarjetas

`GET /api/cards/export`

Requiere `cards.download`.

Query params: acepta los mismos filtros de `GET /api/cards` mas `format`.

`format`: `xlsx`, `excel`, `csv`, `txt` o `pdf`. Default `xlsx`.

Response `200`: archivo descargable. El backend aplica filtros y alcance igual que el listado, ignora paginacion y limita la exportacion a `5000` filas.

## Listar por combustible de diseno

`GET /api/cards/by-design-fuel/:designFuelId`

Path params: `designFuelId` UUID del combustible.

Query params: `page`, `limit`, `search`, `all`, `status`.

Valida que el combustible exista y este activo. `search` usa los mismos campos del listado general.

Response `200`: resultado paginado de `Card` filtrado por `designFuelId`.

## Validar tarjeta local

`POST /api/cards/validate`

Permiso: `cards.validate`.

```json
{
    "clientId": "CLI-001",
    "nip": "1234",
    "vigencia": "1228"
}
```

Requeridos: `clientId`, `nip`, `vigencia`.

Esta accion es sensible porque recibe `nip` y `vigencia`. No debe mostrarse como boton principal del listado salvo que el flujo operativo lo requiera; nunca registres esos campos en logs del frontend.

El backend busca una tarjeta local asignada al `clientId` dentro del alcance del usuario, obtiene datos sensibles desde Cardcloud y valida contra el proveedor. Si la validacion no corresponde al `externalId` local, responde error.

Response `200`:

```json
{
    "valid": true,
    "card": {
        "id": "ff2584aa-e2fc-4d75-b11c-61e447f3cbb0",
        "externalId": "019cd4ad-38dd-7125-a68a-209519d79869",
        "clientId": "CLI-001",
        "maskedPan": "****1234",
        "status": "active",
        "subCompanyId": "79d03f1d-3da4-478e-806e-75ef9d86c992",
        "vehicleId": "db28024c-9ed7-4318-84df-eb399ebd9e7e",
        "assignmentMode": "vehicle"
    }
}
```

## Crear

`POST /api/cards`

Uso recomendado: excepcional/manual. En el flujo normal, primero sincroniza/ubica stock desde `cardcloud-stock` y despues administra la tarjeta local desde este modulo.

```json
{
    "subCompanyId": "79d03f1d-3da4-478e-806e-75ef9d86c992",
    "vehicleId": "db28024c-9ed7-4318-84df-eb399ebd9e7e",
    "designFuelId": "e9ef8b38-c983-4b9c-a51c-7d39ff7b1c84",
    "externalId": "CARD-001",
    "status": "active",
    "assignedAt": "2026-07-04"
}
```

Requerido: `subCompanyId`. Debe estar activo y pertenecer a la compania enviada en `X-Company-Id`.

Opcionales: `vehicleId`, `designFuelId`, `externalId`, `status`, `assignedAt`. Si se envia `vehicleId`, la tarjeta queda en `assignmentMode: vehicle`; si no, queda `unassigned`.

Response `201`: `Card`.

## Asignar tarjetas a subcompania

`POST /api/cards/assign-sub-company`

Permiso: `cardcloud-stock.sub-company.assign`.

Esta accion existe para compatibilidad y para flujos contextuales. En UI principal debe vivir en `Stock Cardcloud`, no como accion primaria del modulo Tarjetas.

```json
{
    "subCompanyId": "79d03f1d-3da4-478e-806e-75ef9d86c992",
    "cards": ["019cd4ad-38dd-7125-a68a-209519d79869"]
}
```

Requeridos: `subCompanyId`, `cards`.

Flujo:

- Valida que la subcompania este activa, pertenezca al `X-Company-Id` y tenga `cardcloudSubaccountId`.
- Llama primero a Cardcloud `/v1/account/cards/assign_bulk` usando `subaccount_id = subCompany.cardcloudSubaccountId`.
- Si Cardcloud confirma, crea o mueve las `Card` locales por `externalId`.
- Si existe el registro en el espejo `Cardcloud`, actualiza `subCompanyId` y `assignedCardId`.

Response `201`:

## Asignar tarjetas a subcompania por Excel

`GET /api/cards/assign-sub-company-excel`

Permiso: `cardcloud-stock.sub-company.assign`.

Descarga archivo `.xlsx` con hoja `Asignacion` precargada solo con tarjetas disponibles: registros de `cardcloud-stock` con `subCompanyId = null`, `assignedCardId = null` y `clientId` presente. Para seleccionar que tarjetas asignar, el operador debe eliminar del archivo las filas que no quiera procesar y subir el archivo con los `clientId` que permanecen.

Columnas:

| Columna          | Requerida | Uso                                                                    |
| ---------------- | --------- | ---------------------------------------------------------------------- |
| `clientId`       | Si        | ID de cliente de Cardcloud. El backend lo usa para resolver la tarjeta. |
| `maskedPan`      | No        | Referencia visual de la tarjeta enmascarada.                           |
| `providerStatus` | No        | Estado crudo recibido de Cardcloud.                                    |

Response `200`: archivo Excel `plantilla-asignacion-tarjetas.xlsx`.

`POST /api/cards/assign-sub-company-excel`

Permiso: `cardcloud-stock.sub-company.assign`.

Content-Type: `multipart/form-data`.

Body:

| Campo          | Tipo     | Requerido | Descripcion                                                        |
| -------------- | -------- | --------- | ------------------------------------------------------------------ |
| `subCompanyId` | `string` | Si        | Subcompania destino. El backend deriva su `cardcloudSubaccountId`. |
| `file`         | `file`   | Si        | Archivo `.xlsx` con la plantilla o columnas compatibles.           |

Reglas:

- Solo procesa la primera hoja del archivo.
- La columna `clientId` es obligatoria y es la llave que se procesa.
- `maskedPan` y `providerStatus` son referencias. El backend no usa esas columnas para resolver la asignacion.
- Acepta encabezados equivalentes para `clientId`, por ejemplo `client_id`, `client id`, `clienteId` o `cliente id`.
- Por compatibilidad, si un archivo antiguo trae `card`, `subCompany` o `description`, el backend las ignora para resolver la asignacion y solo las devuelve como contexto en el resultado por fila.
- Omite filas completamente vacias.
- Marca como fallidas las filas sin `clientId`, `clientId` duplicados dentro del archivo, `clientId` no encontrados, `clientId` ambiguos y filas que excedan el limite.
- Procesa maximo `100` tarjetas por archivo, igual que la asignacion JSON.
- Busca cada `clientId` contra el stock local disponible: sin subcompania local, sin tarjeta local asignada y visible como stock libre. Si encuentra exactamente una tarjeta, toma su `externalId` interno de Cardcloud para enviarlo al proveedor.
- Valida que la subcompania este activa, pertenezca al `X-Company-Id` y tenga `cardcloudSubaccountId`.
- Llama primero a Cardcloud `/v1/account/cards/assign_bulk` con `subaccount_id = subCompany.cardcloudSubaccountId`.
- Solo despues de respuesta correcta sincroniza las tarjetas locales y el espejo `cardcloud-stock`.
- Al terminar crea una notificacion para el usuario que ejecuto la carga con resumen de exitos, fallos y omitidas.

Response `201`:

## Obtener

`GET /api/cards/:id`

Path params: `id` UUID de la tarjeta.

Response `200`: `Card`.

## Movimientos

`GET /api/cards/:id/movements`

Permiso: `cards.movements.read-list`.

Query params: `from`, `to`.

El backend valida que la tarjeta local pertenezca al alcance de la compania y usa `externalId` para consultar movimientos externos en Cardcloud.

Response `200`: respuesta cruda del proveedor Cardcloud para movimientos de tarjeta.

`GET /api/cards/:id/movements/export`

Permiso: `cards.movements.read-list`.

Query params: acepta `from`, `to` y `format`.

`format`: `xlsx`, `excel`, `csv`, `txt` o `pdf`. Default `xlsx`.

Response `200`: archivo descargable. El backend valida que la tarjeta local pertenezca al alcance de la compania, resuelve `externalId` y exporta hasta `5000` movimientos externos devueltos por Cardcloud.

## Actualizar

`PATCH /api/cards/:id`

Acepta `designFuelId`, `externalId` y `status`, todos opcionales. Si la tarjeta ya tiene vehiculo, el `designFuelId` debe coincidir con el combustible del vehiculo.

Response `200`: `Card` actualizada.

## Asignar vehiculo

`PATCH /api/cards/:id/assign-vehicle`

```json
{
    "vehicleId": "db28024c-9ed7-4318-84df-eb399ebd9e7e",
    "assignedAt": "2026-07-04"
}
```

La tarjeta y el vehiculo deben estar activos, pertenecer a la misma sub-compania y respetar `designFuelId` si existe. Si se envia `X-Company-Id`, ambos deben pertenecer a esa compania.

Response:

```json
{
    "id": "ff2584aa-e2fc-4d75-b11c-61e447f3cbb0",
    "vehicleId": "db28024c-9ed7-4318-84df-eb399ebd9e7e",
    "assignmentMode": "vehicle",
    "assignedAt": "2026-07-04T00:00:00.000Z"
}
```

## Actualizar asignacion

`PATCH /api/cards/:id/assignment`

Permiso: `cards.assignment.update`.

```json
{
    "assignmentMode": "vehicle",
    "vehicleId": "db28024c-9ed7-4318-84df-eb399ebd9e7e",
    "assignedAt": "2026-07-04"
}
```

`assignmentMode` acepta `vehicle` o `unassigned`. Si `assignmentMode` es `unassigned` o `vehicleId` es `null`, el backend quita la asignacion. Si se asigna a vehiculo, aplica las mismas reglas de `PATCH /api/cards/:id/assign-vehicle`.

Nota: el modelo actual no tiene asignacion directa a conductor ni modo `locked`; este endpoint es compatible de path, pero funcionalmente cubre solo `vehicle` y `unassigned`.

## Notas para frontend

Este modulo tambien aplica las reglas CRUD de `Frontend Guidelines`: crear con campos visibles/derivados, editar solo campos documentados en `Actualizar`, confirmar desactivacion y refrescar el listado despues de cada mutacion.

### Para que sirve Tarjetas

`Tarjetas` administra la tarjeta local operativa que ya pertenece a la compania/subcompania seleccionada. Sirve para consultar detalle, datos del espejo Cardcloud, movimientos, estado local, combustible de diseno, vehiculo asignado y desactivar/asignar en la operacion diaria.

No reemplaza `Stock Cardcloud`. `Stock Cardcloud` sincroniza tarjetas del proveedor y decide en que subcompania quedan ubicadas. Una vez ubicada, aparece como tarjeta local para operacion.

El bloque `stock` viene del espejo local `cardcloud-stock`; no llama a Cardcloud externo durante `GET /api/cards`. El `balance` se devuelve descifrado como string decimal. No permitas editar `stock.externalId`, `stock.maskedPan`, `stock.clientId`, `stock.balance` ni `stock.providerStatus` desde Tarjetas.

- ID externo: `externalId`, opcional.
- Estado: `status`, con `active` como valor inicial.
- Fecha de asignacion: `assignedAt`, opcional y visible solo cuando se asigna vehiculo.

No muestres `assignmentMode` como campo editable. Es un estado derivado por backend: queda `vehicle` si hay vehiculo asignado y `unassigned` si no lo hay.

Para la accion de asignar vehiculo, muestra vehiculos activos de la misma subcompania. Para quitar asignacion, usa la accion dedicada `PATCH /api/cards/:id/unassign`.

Si el front quiere una sola accion compatible con el contrato anterior, puede usar `PATCH /api/cards/:id/assignment`; internamente solo soporta asignar a vehiculo o quitar asignacion.

Para asignar tarjetas a una subcompania, el usuario debe seleccionar la subcompania y las tarjetas desde una lista controlada; nunca debe escribir `subaccount_id`. El backend deriva la subcuenta desde `cardcloudSubaccountId`. Como accion principal individual, usa preferentemente `PATCH /api/cardcloud-stock/:id/assign-sub-company` desde Stock Cardcloud. Para carga masiva por archivo, usa `GET /api/cards/assign-sub-company-excel` y `POST /api/cards/assign-sub-company-excel`.

Si la tarjeta se crea sin vehiculo, dejala como `unassigned` y ofrece la asignacion como accion posterior. Si se crea desde el detalle de un vehiculo, deriva `vehicleId`, `subCompanyId` y `assignedAt` desde ese contexto cuando aplique.

## Errores comunes

| Estado | Caso                                                                  |
| ------ | --------------------------------------------------------------------- |
| `400`  | Datos relacionados no validos, fecha invalida o parametros invalidos. |
| `401`  | Request sin autenticacion valida.                                     |
| `403`  | Usuario autenticado sin el permiso requerido.                         |
| `404`  | Tarjeta no encontrada.                                                |
| `409`  | Conflictos de unicidad segun constraints Prisma.                      |
